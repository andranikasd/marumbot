# Marum — bottleneck and design review

Read-only audit of the bot setup on branch `codex/performance-budget-flow`, dated
2026-09-03. No source file was modified. Findings come from reading the code and
the deployment definitions; none of them were measured against a running system,
so the "Impact" column states the mechanism rather than an observed number.

Scope covered: the Cloudflare edge (`deploy/cloudflare/worker`), the Go binary
wiring (`cmd/marum`), the inbound Telegram adapter, the command worker and its
scheduled walks, the Postgres adapter and its queries, the Mini App server, and
the Mini App browser bundle.

Severity key: **High** — limits throughput, latency or availability today, or
will do so at a small multiple of current load. **Medium** — measurable cost or
a structural weakness that will become expensive. **Low** — worth fixing when
the surrounding code is next touched.

## Performance and scalability

| # | Severity | Area | Location | Description | Impact | Suggested direction |
|---|---|---|---|---|---|---|
| P1 | High | Deployment topology | `deploy/cloudflare/worker/index.ts:137` | Every request — webhook updates, Mini App API calls, health probes and the scheduler tick — is routed to a single container instance via `getContainer(env.MARUM_APP, "singleton")`. The stated reason is to keep "the token bucket inside the Go sender" global, but no such token bucket exists anywhere in `internal/adapter/out/telegramclient`. | The system has one process worth of CPU and one connection pool for all traffic, and no horizontal scaling path. A single container restart is a full outage. The justification for accepting that ceiling is not true of the current code. | Either implement the outbound limiter the comment assumes and keep the singleton as a deliberate trade, or shard by chat id and move rate limiting to a shared store so instances can be added. |
| P2 | High | Database | `internal/adapter/out/postgres/postgres.go:33` | `cfg.MaxConns = 8` is hardcoded, with no `MinConns`, no environment override, and no pool metrics exported. | Combined with P1, eight connections is the concurrency ceiling for the entire deployment. Once they are all in use, requests block inside `pool.Acquire` with no timeout of their own and no signal that queuing is happening — the symptom is uniform slowness with no attributable cause. | Make max/min connections configurable, set `MinConns` above zero so a woken container does not handshake on the first request, and export `pool.Stat()` as gauges. |
| P3 | High | Outbound Telegram | `internal/adapter/out/telegramclient/client.go` (whole file) | The package doc claims a single sender exists so that "Telegram's limits are per bot rather than per process", and `worker/index.ts:135` calls it a token bucket, but there is no rate limiter, no concurrency cap and no queue. `SendDueReminders` delivers up to 50 messages per tick and `RefreshMenuButtons` walks every account, both as fast as the loop runs. | Bursts exceed Telegram's global send limit, which returns 429. The 429 handling is correct but reactive: the backoff pushes work to the next tick, which bursts again. Reminder delivery degrades exactly when there is most of it to do. | Add a real token bucket in front of `call`, sized to Telegram's documented global and per-chat limits, and let it be the one place sends are paced. |
| P4 | High | Request path | `internal/app/worker.go:238` | Every single inbound command calls `SetChatMenuButtonFor` before doing any work, on the reasoning that an account missed by a rollout sweep should converge. `apply` then also sends a `SendChatAction` typing indicator. | A `/start` costs three sequential Telegram round trips before the reply is sent, inside the 10 second `drainBudget` (`internal/adapter/in/telegram/webhook.go:174`) that bounds the synchronous webhook path. The menu call is a no-op for almost every user, and it consumes the rate-limit budget of P3 on every message. | Record the menu button's version per account and call Telegram only when it differs from `AppVersion`, or move the refresh entirely into the tick. |
| P5 | High | Startup | `internal/app/menu.go:169` | `RefreshMenuButtons` pages through every account at process start, and for each one performs a chat-id lookup and a Telegram API call, sequentially, inside a 30 second context (`cmd/marum/main.go:222`). | Past a few hundred accounts the context expires mid-walk, so the sweep never completes and partially reruns on every deploy. It is also the largest single Telegram burst the system produces, at the moment the container is coldest. | Move the sweep off the startup path onto a paced background job with its own budget and a cursor that survives restarts, and drive it through the limiter from P3. |
| P6 | High | Scheduler | `internal/app/reminders.go:78` and `:115` | `TickReminders` walks up to 500 accounts sequentially. For each one, `ScheduleForUser` re-lists the loans, rebuilds every schedule, and issues one `ScheduleReminders` database round trip per instalment inside the horizon. Nothing is batched and nothing runs in parallel. | Hundreds to low thousands of sequential queries execute inside one HTTP tick request, on the same eight connections everything else shares. The tick's duration grows linearly with the user base, and the inbox drain that shares the request (`cmd/marum/main.go` `tickHandler`) waits behind it. | Batch occurrence writes into a single multi-row statement per account, give each walk stage its own deadline, and consider bounded parallelism with a worker group that the process can wait on. |
| P7 | Medium | Scheduler | `cmd/marum/main.go` `tickHandler` | One tick request performs three unrelated walks — inbox drain, reminders, shadow recommendations — with a single shared deadline and no per-stage budget. | A slow reminder or shadow walk delays the inbox drain, which is the only stage a user can perceive. The failure is invisible because all three are reported under one "tick" span. | Give each stage its own timeout and span, and drain the inbox first and unconditionally. |
| P8 | Medium | HTTP client | `internal/adapter/out/telegramclient/client.go:47` | The client uses `http.DefaultTransport`, whose `MaxIdleConnsPerHost` is 2. All traffic goes to one host, `api.telegram.org`. | Beyond two concurrent sends, connections are opened and discarded rather than reused, so bursts pay a fresh TLS handshake per message — the exact workload where latency matters most. | Give the client its own `http.Transport` with `MaxIdleConnsPerHost` and `MaxConnsPerHost` set to match the intended send concurrency. |
| P9 | Medium | Compute | `internal/app/loans.go:303` | `UserLoan.Schedule()` calls `amortisation.Build` every time and memoises nothing. In `/loans` alone it is invoked once per loan in `positions`, again in `nextInstalment`, and again in the render loop. | The most expensive per-loan computation runs roughly three times per loan per request, in both the bot list and the Mini App list. | Build the schedule once per loan per request and pass it down, or memoise on the value since the inputs are immutable for the life of the struct. |
| P10 | Medium | Compute | `pkg/core/plan/search.go` | The candidate policies explored by `Explore`/`Rank` are pure and independent, and the code describes the search as the most expensive computation in the system, but every candidate is simulated on one goroutine. | Plan latency is bounded by single-core speed even though the work is embarrassingly parallel, and the container has more than one core available. | Fan the per-policy simulations out across a bounded worker group owned by the caller, keeping the deterministic ranking on the merged results. |
| P11 | Medium | Caching | `internal/app/plancache.go:31`, `deploy/cloudflare/worker/index.ts:19` | The plan search cache is process-local and in-memory, capped at 256 entries, while the container is configured with `sleepAfter = "10m"`. | Every container sleep discards the cache, so the first plan opened after an idle period always pays the full search — and idle periods are common by design. The cache helps repeat opens within one waking period only. | Persist the report keyed by its fingerprint (the fingerprint already encodes engine version and valuation date, so staleness is handled), or accept the limitation explicitly in the comment. |
| P12 | Medium | Caching | `internal/app/plancache.go:128` | `searchFingerprint` walks the whole input tree by reflection, builds a length-framed string and hashes it with SHA-256 — on every call, including cache hits. Eviction (`evictLocked`) scans the entire map and removes a single entry when full. | The lookup cost is paid before the cache can save anything, and eviction degrades to a full scan per insert once the map is at capacity. | Build the fingerprint incrementally from typed fields rather than reflection, and keep an eviction order (a heap or an intrusive list) instead of scanning. |
| P13 | Medium | Mini App payload | `internal/adapter/in/miniapp/web/js` (328 KB across 31 modules), `web/index.html` | The browser bundle ships unbundled and unminified. `main.js` eagerly imports all sixteen screen modules regardless of which screen was requested; `index.html` declares `modulepreload` for eleven files, so the rest are discovered as the parser walks the import graph. | A cold open on a phone fetches around thirty separate files, most of which the session will never use, and the unpreloaded ones arrive in waterfall order. This is the dominant cost of the first Mini App open. | Add a build step that bundles and minifies, and split the entry point so a deep link loads its screen plus the shell rather than all sixteen. |
| P14 | Medium | Mini App transport | `internal/adapter/in/miniapp/server.go` (whole file) | Nothing in the Go binary compresses responses; there is no gzip or Brotli middleware anywhere in `internal/` or `cmd/`. Compression exists only on the Cloudflare asset path. | Self-hosted deployments and the container fallback path in `worker/index.ts` serve the full uncompressed 328 KB of JavaScript and 24 KB of CSS. Text assets of this kind typically compress by three to four times. | Wrap the asset routes in a compressing handler that honours `Accept-Encoding`, or pre-compress the embedded files at build time and serve the encoded variant. |
| P15 | Medium | Mini App client cache | `internal/adapter/in/miniapp/web/js/api.js` | `getJSON` always calls `fresh(path)`, and `fresh` consults only the in-flight map — never the 30 second `cache`. The cached body is returned solely in the `TypeError` branch, meaning only when the network failed. | What the code calls a cache never saves a request. Re-entering a screen inside its TTL still performs a full round trip, so tab switching costs one request per visit per path. | Either serve inside the TTL and label the data as such, or rename the structure to what it is — an offline fallback store — so the next reader does not assume warm reads are free. |
| P16 | Medium | Mini App server | `internal/adapter/in/miniapp/server.go:809`, `:853` | `shell` re-reads `index.html` from the embedded filesystem and re-runs the `shellRef` regex substitution on every request. `withTokens` re-reads `styles.css` and re-concatenates the design tokens on every request, and writes the body directly rather than through `http.ServeContent`. | Per-request work that is identical for the life of the process, and the stylesheet path loses `ETag`, `Last-Modified` and range support, so conditional requests always transfer the full body. | Compute both bodies once at construction time and serve them with `http.ServeContent` and a content-derived `ETag`. |
| P17 | Medium | Request fan-out | `internal/adapter/in/miniapp/server.go` (`authed`, `getBudget`, `listLoans`) | Each Mini App API call performs its own sequential chain: verify init data, resolve the account by tag, resolve the business date (another user read), then read the resource. `getBudget` additionally calls `RequiredThisMonth`, which re-lists and re-projects the same loans the handler is already working with. | Three to five sequential database round trips per API call, on the pool from P2, for data that is constant within a request. | Resolve the account and its business date once per request and carry them on the context; pass the already-loaded loans into `RequiredThisMonth` instead of re-reading them. |
| P18 | Low | Request fan-out | `internal/app/advice.go:523` | `positions` issues an `AdminProfileFlag` database read inside the per-loan loop, deduplicated only by a map built during that same loop. | Up to one extra round trip per distinct lender profile on every plan and every loan list. The untracked `internal/app/profile_flag_dedup_test.go` appears to address exactly this, so it is noted for completeness. | Read the flags for the distinct profile set in one query before the loop. |
| P19 | Low | SQL | `queries/loans.sql:51` (`ListLoansForUser`) | The projection carries four correlated `EXISTS` subqueries over `loan_events` and `snapshot_event_coverage` per loan row, alongside three lateral joins, and casts dates and numerics to text. | Bounded by the twelve-loan product limit, so it is not urgent, but it is the hottest read in the system and its cost grows with each borrower's event history rather than with their loan count. | Consider materialising the "has unreconciled payments" predicate as a column maintained on write, since it is read far more often than it changes. |
| P20 | Low | Edge | `deploy/cloudflare/worker/index.ts` `scheduled` | The tick is dispatched with `ctx.waitUntil` and no timeout or result check. | A tick that hangs is invisible: nothing observes its duration or its failure, and the next cron fires regardless. | Give the forwarded request an `AbortSignal` deadline and log a non-2xx result. |

## Design

| # | Severity | Area | Location | Description | Impact | Suggested direction |
|---|---|---|---|---|---|---|
| D1 | High | Correctness of documentation | `deploy/cloudflare/worker/index.ts:135`, `internal/adapter/out/telegramclient/client.go:1`, `AGENTS.md` | Three separate places describe an outbound rate limiter that does not exist, and the singleton deployment topology is justified by it. `AGENTS.md` separately records that the `pkg/core/rates` invariant references a package with no implementation. | Comments here are load-bearing: they are how the next reader decides what is safe. Two known cases of a documented guarantee with no code behind it means the rest cannot be trusted without checking. | Treat this as one task: either build the missing mechanism or delete the claim. Prefer building it, since P3 needs it anyway. |
| D2 | High | Local development | `internal/config/config.go:47`, `:95` | `MARUM_MODE` defaults to `polling` and validation accepts it, but no polling implementation exists anywhere in the repository — `getUpdates` appears in no file. The only inbound transport is the webhook. `README.md` and `AGENTS.md` both state that local development uses long polling. | A developer following the documented quick start gets a bot that starts cleanly, reports healthy, and silently receives nothing. The configuration validates a mode the binary cannot serve. | Either implement the poller or remove the mode, and correct both documents. Refusing to start on `polling` would be better than the current silence. |
| D3 | Medium | Layering | `internal/app/worker.go:63` | `Worker` takes roughly twenty injected ports, holds four pieces of mutable atomic state and two caches, and simultaneously acts as the command handler, the reminder engine, the shadow walker, the menu publisher, and the Mini App's `Required`, `Filed`, `Planner` and `Reviser` implementations. | Everything depends on this one type, so nothing that touches it can be tested, deployed or scaled apart from everything else. It is also why the scheduler and the request path share a process and a connection pool. | Split along the existing seams: the command handler, the scheduled walks, and the read surface the Mini App consumes are three separable objects that happen to share stores. |
| D4 | Medium | Layering | `internal/app` (41 files, one package) | Every use case in the system lives in one Go package. Consumer-declared interfaces are followed correctly, but the dependency graph the architecture describes has a single node in the middle. | Package boundaries cannot enforce anything internal to `app`, so the discipline is entirely convention. Compile times and test scope are both whole-package. | Consider sub-packages along the same seams as D3, keeping the port interfaces with their consumers as the house style requires. |
| D5 | Medium | Durability model | `internal/adapter/in/telegram/webhook.go:150-175` | The inbox exists so that a crash cannot lose an update, and the comment argues that persisting first is what provides that property. The handler then calls `Handle` synchronously with a 10 second budget so the reply is not deferred to the tick. | The design pays for the queue and still couples business latency to Telegram's webhook timeout. A slow database shows up as webhook latency and, past the budget, as work that silently falls through to the tick — which is the behaviour the inline call was added to avoid. | This is a deliberate trade and may be the right one, but it should be stated as such, with the drain budget derived from a measured p99 rather than a round number. |
| D6 | Medium | Observability | `internal/obs/metrics.go` | Instruments exist for database query duration, database errors, admin sign-ins, ledger replay and accrual overflow. There is nothing for webhook end-to-end latency, Telegram API latency or 429 rate, plan search duration, plan cache hit ratio, connection pool saturation, tick duration, or inbox queue depth. | None of the findings above can be confirmed, prioritised or regression-tested from production telemetry. `/status` exposes queue ages, but only to whoever polls it. | Add histograms for the four hot paths (webhook, Telegram send, plan search, tick) and gauges for pool saturation and queue depth. All have naturally bounded label sets. |
| D7 | Medium | Back pressure | `cmd/marum/main.go` `publicRoutes` | There is no load shedding anywhere: no bounded worker pool, no queue-depth threshold, no admission control. The tick drains a fixed batch of 25 and the webhook path is unbounded in concurrency, limited only by the connection pool blocking. | Under overload the system degrades by making every request slow rather than by rejecting some quickly, which is the failure mode that also breaks the health probes. | Bound in-flight webhook handling explicitly and return a retryable status when the bound is reached — Telegram will redeliver, which is the correct behaviour. |
| D8 | Low | Schema coupling | `internal/adapter/in/telegram/update.go:62` and `internal/app/worker.go:29` | The command-kind constants are duplicated in both packages, deliberately, with a comment acknowledging that a shared literal repeated twice is how the two drift apart. These values are persisted, so a mismatch orphans rows. | The stated risk is accepted without a mechanism that catches it. Nothing fails if one list changes. | A small shared value package (not a `utils` package — a named domain type) or a test that asserts the two sets are equal would close it at no architectural cost. |
| D9 | Low | Dead configuration | `internal/config/config.go:29`, `:58` | `MARUM_TICK_INTERVAL` is parsed, validated, and stored on `Config`, and then read by nothing. Scheduling lives in the Cloudflare cron. | A setting that appears configurable and silently does nothing. Someone will eventually change it to fix a problem and conclude the tick is broken. | Remove it, or wire it to a self-hosted in-process ticker for deployments without the Worker. |
| D10 | Low | Mini App structure | `internal/adapter/in/miniapp/web/js/main.js` | The plug-in screen model requires every screen to be imported by the entry point to register itself, which is what makes the eager loading in P13 structural rather than incidental. | Code splitting cannot be added without changing the registration model, so P13 is not a build-tool-only fix. | Register screens lazily by id with a dynamic `import()` factory, so the navigator can load a screen the first time it is shown. |

## Not covered

The admin interface (`internal/adapter/in/admin`), the ledger and allocation
engines under `pkg/core` beyond the plan search, the Terraform definitions, and
the migrations' historical correctness were not reviewed. No load testing was
run; the `deploy/observability/k6` profile exists and would be the natural way
to confirm P1, P2, P4 and P13 before acting on them.
