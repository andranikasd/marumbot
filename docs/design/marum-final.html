1 · What this is

Marum keeps a borrower's loans in one place, reminds them before each due date, records what they paid, and computes a repayment plan. It moves no money, holds no bank credentials, recommends no lender, and contains no AI. Every number is deterministic and traceable to an input.

Four boundaries the design is built on

  1. A Telegram update becomes a durable command before Telegram receives 200 OK.
  2. User-reported facts are append-only. Balances and payment splits are rebuildable caches.
  3. A bank-confirmed snapshot is the authoritative anchor. Marum never invents historical bank state.
  4. Message delivery is at-least-once. Rare duplicates are accepted, worded for, and measured.

Out of the MVP

Fee-aware min_cost optimisation · variable rates · declining-principal loans · revolving cards · delinquent or restructured loans · cross-currency planning · effective-rate comparison · OCR · bank integrations · Telegram Stars. Each returns only after the ledger and engine are proven against real Armenian schedules.

2 · Architecture

ComponentResponsibility
CloudflareDNS, TLS, WAF, DDoS. No business logic, no application secrets.
webhookValidates the secret-token header before reading the body, bounds and normalises the update, inserts a durable command, answers 200 only after commit.
command workerLeases a command with a fencing token, applies the whole business effect in one transaction, completes the command with the same token.
scheduler60-second tick under a transaction-scoped advisory lock. Generates reminder occurrences, groups them into deliveries, runs reconciliation. Catch-up tick on startup — it never assumes the previous minute ran.
senderExactly one active leader, holding a session-level advisory lock on a dedicated connection. 28 msg/s global, 1 msg/s per chat — meaningful because the bucket is genuinely global.
pkg/corePure engine. No database, network, filesystem, clock, randomness, or logging. Time enters as a parameter.
backup jobSeparate schedule and credential, direct connection. Dump, encrypt, upload, verify, restore-drill.
PostgreSQLSystem of record: durable inbox, ledger, snapshots, derived state, occurrences, delivery outbox.

Two instances may run for webhook availability. Command processing is safely concurrent through leases; sending is not, and the advisory lock enforces that. During a leader handover there is a brief window where both instances believe they hold the role: the send rate may briefly exceed 28/s, which Telegram absorbs as throttling, and a delivery may be attempted twice — the fencing token turns that into one successful mark and one rejection.

No Redis, no broker, no serverless container, no microservices.

3 · Reliability invariants

Implementation requirements, not aspirations. Each is testable, and each has a named failpoint test in Marum-Reliable-MVP-Design.md §17.4.

#InvariantConsequence
R1Acknowledgement means durable acceptance200 OK only after the command commits. A crash after the response cannot lose the action.
R2One update causes at most one business effecttelegram_update_id is permanently unique — it survives account erasure with the payload cleared. Every financial event also carries its own idempotency key.
R3Facts are append-onlyPayments, snapshots, voids and billing events are never edited. A mistake is superseded or voided by another row.
R4Derived state is disposableloan_state and allocation results can be deleted and rebuilt from the anchor snapshot plus active events.
R5A bank snapshot outranks Marum's reconstructionA confirmed snapshot becomes the new replay anchor. Drift is measured, never hidden, and never corrected twice.
R6No silent financial assumptionsEvery projection carries its assumption ledger: day count, rounding, contract version, snapshot date, allocation policy, prepayment behaviour, missing fields.
R7Delivery is at-least-onceThe gap between Telegram accepting and Marum recording message_id cannot be closed. Reminder text reads correctly if it arrives twice.
R8No network I/O inside a transactionTelegram, object storage and telemetry calls happen only after commit.
R9Money is never floating pointint64 minor units, checked arithmetic, explicit rounding policy. See §6.
R10Business dates are not timestampsDue dates and value dates are date-only. Time zones apply only when converting a local reminder slot to an instant.
R11Deletion survives restoreAn encrypted deletion journal lives outside the backup chain and is replayed after any restore.
R12Stale or unsupported state cannot produce a confident planThe eligibility guard is centralised and cannot be bypassed by a handler. See §7.

4 · Processing model

Why a durable inbox rather than a dedup table

A table holding only update_id is unsafe: if the row is inserted and the process dies before the action is applied, Telegram's retry is discarded as a duplicate and the user's payment is silently lost. The inbox stores the normalised command and its processing state, so a retry finds work still pending.

The business transaction

For a payment-recording command, one transaction does all of this or none of it:

  1. Lock the command by its lease token.
  2. Lock the loan's event-sequence row.
  3. Confirm no financial event already uses this idempotency key.
  4. Insert the immutable payment fact.
  5. Advance or rebuild derived state.
  6. Write a versioned allocation result.
  7. Cancel and regenerate affected future reminder occurrences.
  8. Enqueue the reply delivery.
  9. Complete the command with its fencing token.

The webhook does not store the raw Telegram payload. Input resembling credentials or card data produces a reject_sensitive_input command with the value discarded.

5 · Domain model

LayerRule
Loan identityHolds no financial terms and no balance. Just the enduring user-owned record.
Contract versionsA restructuring, rate change or maturity change creates a new version. Effective periods may not overlap. Every event records the version under which it was interpreted.
Bank snapshotsAn observation of lender state at the end of a stated business date, split into independently allocatable buckets: principal, accrued interest, unpaid interest, current fees, overdue fees, penalties, overdue principal, advance credit, next instalment. Trust is user_entered, bank_confirmed, or imported_verified. Only bank_confirmed resets drift.
Loan eventsWhat the user reported, not Marum's interpretation. Five kinds: payment_reported, prepayment_reported, bank_fee_reported, entry_voided, loan_closed_reported. There is no generic correction event — a new snapshot corrects state.
Allocation resultsThe split into interest, fees, penalties, overdue and scheduled principal, extra principal or advance credit. Stored separately from the fact, stamped with policy version, contract version, engine version, replay generation and confidence. A late earlier event supersedes the result; it never rewrites it.
Derived stateanchor snapshot + active events + policy interpretation, carrying an event_set_hash. Nightly reconciliation recomputes it; a mismatch rebuilds the cache and raises an alert.
ProjectionSchedules and plans are function results. No table.

5.1 The two rules that stop double-counting

Snapshot boundary. When an event arrives with value_date <= anchor.as_of, Marum asks whether the bank balance already included it. Yes writes an immutable coverage assertion and the event is kept for audit but not re-applied. No or unknown sets the loan to needs_reconciliation and asks for a fresh balance.

Two orders, never conflated. recorded_seq is gapless per loan and records the order Marum learned things. Financial replay orders by value_date, then the lender's bank_order where supplied, then recorded_seq as a deterministic tie-break.

6 · Money, dates, accrual

ConcernRule
Representationint64 minor units with the currency in the type. AMD has 100 minor units to the dram; whole-dram input is multiplied by 100.
Settlement roundingDefault unit is 100 minor units — lenders settle in whole drams. A different unit requires a real schedule to confirm it.
RatesScaled integers in the core (parts per billion); numeric(12,9) in PostgreSQL. Never through float64.
DatesDate-only in the core. Due-date clamping is centralised: the 31st falls to the last day of a shorter month and returns the following month.
InstalmentInteger bisection for the smallest instalment that closes the dated schedule, using the same builder as projection. The closed-form annuity formula is a test cross-check and an initial bound — never authoritative for irregular periods.
Accrual must not be evaluated in 64-bit arithmetic

interest = principal × rate × days / denominator overflows int64 at ordinary local loan sizes:

Loan @ 18%× rate× 31 daysint64
4,000,000 AMD7.2 × 10¹⁶2.2 × 10¹⁸fits
16,529,340 AMD—9.22 × 10¹⁸last value that fits
30,000,000 AMD5.4 × 10¹⁷1.7 × 10¹⁹overflow
80,000,000 AMD1.44 × 10¹⁸4.5 × 10¹⁹overflow — 66 bits

At a card rate of 26% the ceiling falls to about 11,443,389 AMD. Compute the numerator in a 128-bit intermediate (math/bits.Mul64 with a 128÷64 division), then divide and round once. Do not reorder into (principal × days) / denom × rate — that dodges the range problem by rounding twice and silently changes the schedule. Overflow is a typed error, never a wrap.

7 · Eligibility

Planning is gated, but the gate is graded. A single confirmed-and-fresh check in front of every calculation would refuse most users most of the time, and a tool that usually refuses is one people stop opening.

TierConditionMay show / must not show
confidentSupported contract, bank_confirmed snapshot within the freshness threshold (initially 35 days), no ambiguous pre-snapshot event, no unsupported overdue or penalty state, known allocation and prepayment policy, successful replayPlans, savings, debt-free dates, strategy comparison.
indicativeConfirmed snapshot older than the threshold; nothing else wrongProjections labelled with the snapshot date and its age, next payment, reminders. Not savings figures or a debt-free date stated as fact. Carries a one-tap confirm action that promotes the loan back.
blockedAmbiguous pre-snapshot event, unsupported overdue or penalty state, unknown allocation policy, or failed replayThe ledger, the reminders, and the exact reason. No projection.

The eligibility function returns machine-readable reasons, and those reasons are what the user sees.

7.1 Safe degradation

ConditionBehaviour
Allocation policy unknownRecord the fact, do not claim a balance, ask for the bank-reported figure and use it as the new anchor.
Unpaid interest, penalties, overdue principalReminders continue; optimisation is disabled; ask for an official payoff figure.
Contractual instalment omittedSolve it from the dated schedule, label it calculated, show the assumption.
Prepayment requires a bank requestShow the operational step; do not reduce projected principal until a later snapshot confirms it.
Contract behaviour unsupportedKeep the ledger and reminders; show no savings and no debt-free date.

8 · Data model

The remaining tables are operational rather than financial:

TablePurpose
telegram_commandsThe durable inbox. Unique telegram_update_id, status, attempts, next_attempt_at, lease owner and token, plus trace_context so one trace survives the queue (§11.3.1).
conversation_statesPersisted, optimistic-versioned flow position. Advanced in the same transaction that completes its command, so a redelivery cannot advance it twice.
budgetsMonthly amount, reserve floor, month-keyed overrides. The plan itself is not stored.
reminder_rulesPer-loan offsets and local send time.
reminder_occurrencesOne row per loan fact due to be reminded. Generated 35 days ahead; cancelled and regenerated transactionally when a payment, snapshot or contract change lands.
notification_deliveries + _itemsOne Telegram message bundling several occurrences, carrying trace_context for trace continuity. A partial unique index keeps an occurrence attached to at most one live delivery, so a dead delivery releases its occurrences instead of stranding them.
reconciliation_runsDrift per bucket at each new anchor. Repeated drift on one policy version disables confident planning for it until reviewed.

9 · Reminders and delivery

ConcernRule
AggregationThe scheduler groups a user's due occurrences into one delivery per local send bucket. The delivery row is created shortly before its bucket, not 35 days ahead, so the frozen payload cannot carry a stale balance.
Quiet hours21:00–09:00 in the user's timezone. Deferred reminders group into a 09:00 delivery.
JitterDeterministic, derived from the occurrence ID — spreads the 09:00 spike without becoming irreproducible.
Send-time guardImmediately before sending, the sender checks that at least one attached occurrence is still valid; otherwise the delivery is cancelled. A payment can still land inside the remaining window, so reminder text says "if you have already paid, ignore this or record it here".
Retry429 returns to pending honouring retry_after without blocking other chats. Timeout and 5xx back off exponentially with jitter, six attempts. 403 marks dead and suspends that user's reminders.
BatchingAt most 20 deliveries per claim with a 120-second lease, renewed when processing passes half the lease.

Capacity is sized on bursts, not averages. The binding case is the 09:00 release after quiet hours on a salary day. Collapsing a user's due loans into one message before rows are generated is what keeps that within the SLO — without it the 15-minute target breaks at roughly 20,000 users; with it there is headroom past 50,000.

10.2 External watchdog

One check that must work when everything else does not: an external monitor calls an authenticated status endpoint whose body comes from bounded queries — last successful tick, oldest pending command, oldest pending delivery, expired leases, dead counts, reconciliation mismatches. PostgreSQL is never exposed publicly.

Alerts route through a separate bot token, so a compromise of the product's token cannot silence the alarm about it. Full telemetry design is §11.

10.3 Backups

Two layers. Managed PITR for operational loss — this forces a paid database tier from Phase 2, roughly $19–25/month, and should be budgeted then rather than discovered later. Plus a nightly pg_dump -Fc, separately encrypted, 30 daily and 6 monthly, for logical corruption and provider escape.

A backup counts as successful only after a restore passes: migration verification, constraint checks, application startup, identity decryption for every active key version, replay == loan_state, claim queries, deletion-journal application, and a representative read-only journey. Row counts prove nothing.

10.4 Erasure and restore

Before primary deletion the erasure worker writes a subject tombstone to an encrypted append-only journal held outside the backup chain. Any restore proceeds: restore into an isolated database → apply every journal entry included in or newer than the backup → verify erased subject HMACs are absent → run integrity tests → only then promote. Restoring a backup cannot resurrect an erased account.

11 · Observability

Five signals — traces, metrics, logs, continuous profiles and synthetic checks — all pushed to Grafana Cloud and joined by one trace ID. Deep enough to answer "why was this reminder late" and "which function burned the CPU while it happened", and small enough to stay permanently inside the free tier.

11.1 Design rules

#RuleReason
O1One trace spans the whole user actionA payment crosses the webhook, the command worker and the sender, with durable queues between them. A trace that stops at the webhook explains nothing.
O2Every log line carries trace_id and span_idLog → trace and trace → log are one click. Correlation is not a convention people remember.
O3Histograms carry exemplarsA latency spike on a dashboard links directly to the trace that caused it.
O4No amount, chat ID, lender name, or raw payload in any signalTelemetry leaves the trust boundary and lives 14 days in a third-party system.
O5No unbounded labelFree-tier metrics are billed by active series. A label whose cardinality grows with users is a bill and an outage.
O6Liveness signals are derived from the database, not from the processA gauge in a process that has stopped ticking reports nothing. The thing that is broken cannot be the thing that reports it.
O7Business correctness is instrumented, not only latencyReconciliation drift and reliability-tier distribution are the metrics that say whether the product is telling the truth.

11.3 Pipeline

Traces, metrics and logs travel as OpenTelemetry over OTLP/HTTP to one Grafana Cloud gateway. Profiles use the Pyroscope push protocol to the same stack — OpenTelemetry's profiling signal is not yet stable, and a working profiler today beats a standard one later. No scrape endpoint, no agent, no sidecar: a scrape target would be a second thing to keep alive.

# OTLP — traces, metrics, logs
OTEL_EXPORTER_OTLP_ENDPOINT=https://otlp-gateway-<zone>.grafana.net/otlp
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
OTEL_EXPORTER_OTLP_HEADERS=Authorization=Basic ${GRAFANA_OTLP_TOKEN}   # base64(instanceID:token)
OTEL_SERVICE_NAME=marum
OTEL_RESOURCE_ATTRIBUTES=deployment.environment=prod,service.namespace=marum

# Pyroscope — continuous profiles
PYROSCOPE_SERVER_ADDRESS=https://profiles-<zone>.grafana.net
PYROSCOPE_BASIC_AUTH_USER=<stack-user>
PYROSCOPE_BASIC_AUTH_PASSWORD=<api-token>
func Init(ctx context.Context, cfg Config) (func(context.Context) error, error) {
    res, err := resource.Merge(resource.Default(), resource.NewWithAttributes(
        semconv.SchemaURL,
        semconv.ServiceName("marum"),
        semconv.DeploymentEnvironmentName(cfg.Env),
        semconv.ServiceInstanceID(cfg.InstanceID),
        // service.version is deliberately NOT here — see 11.6.3.
    ))
    if err != nil { return nil, err }

    tp := trace.NewTracerProvider(
        trace.WithResource(res),
        trace.WithSampler(trace.ParentBased(trace.AlwaysSample())),   // see 11.4.4
        trace.WithBatcher(otlptracehttp.NewUnstarted()),
    )
    mp := metric.NewMeterProvider(
        metric.WithResource(res),
        metric.WithReader(metric.NewPeriodicReader(
            otlpmetrichttp.NewUnstarted(), metric.WithInterval(30*time.Second))),
    )
    lp := log.NewLoggerProvider(
        log.WithResource(res),
        log.WithProcessor(log.NewBatchProcessor(otlploghttp.NewUnstarted())),
    )

    // Span profiles: every span carries pprof labels, so Tempo can show the
    // flame graph for one span rather than a process-wide average (11.7.1).
    otel.SetTracerProvider(otelpyroscope.NewTracerProvider(tp))
    otel.SetMeterProvider(mp)
    otel.SetTextMapPropagator(propagation.TraceContext{})   // W3C only, no B3

    // Free coverage: Go runtime metrics — GC, heap, goroutines, scheduler.
    if err := runtimemetrics.Start(
        runtimemetrics.WithMinimumReadMemStatsInterval(10*time.Second)); err != nil {
        return nil, err
    }

    prof, err := startProfiler(cfg)          // 11.7
    if err != nil { return nil, err }

    return func(ctx context.Context) error {
        return errors.Join(prof.Stop(), tp.Shutdown(ctx),
            mp.ForceFlush(ctx), mp.Shutdown(ctx), lp.Shutdown(ctx))
    }, nil
}

Auto-instrumentation is wired at the boundaries every request crosses:

// inbound: route-level RED plus a server span per request
handler := otelhttp.NewHandler(mux, "marum",
    otelhttp.WithFilter(func(r *http.Request) bool { return r.URL.Path != "/healthz" }))

// outbound: every Telegram call becomes a client span inside the delivery span
tgClient := &http.Client{Transport: otelhttp.NewTransport(http.DefaultTransport)}

// database: a span per named query, plus pool metrics
pgCfg.ConnConfig.Tracer = otelpgx.NewTracer(otelpgx.WithTrimSQLInSpanName())
otelpgx.RecordStats(pool)

The health endpoint is filtered out of tracing deliberately: a check every 60 seconds would otherwise be the most-traced operation in the system and would tell nobody anything.

11.4 Traces

11.4.1 Continuity across a durable queue

The interesting problem is not instrumenting a request — it is that a user action is three processes separated by two database tables. The webhook returns before the work happens, and the sender runs minutes later. Two columns solve it:

ALTER TABLE telegram_commands        ADD COLUMN trace_context text;  -- W3C traceparent
ALTER TABLE notification_deliveries  ADD COLUMN trace_context text;

The producer injects the current context at insert time; the consumer extracts it and continues the same trace. One trace_id then covers webhook → command → reply, which is exactly the object a support question is about.

// producer — inside the same transaction that inserts the row
carrier := propagation.MapCarrier{}
otel.GetTextMapPropagator().Inject(ctx, carrier)
cmd.TraceContext = carrier["traceparent"]

// consumer — the lease already returned cmd
ctx = otel.GetTextMapPropagator().Extract(ctx,
    propagation.MapCarrier{"traceparent": cmd.TraceContext})
ctx, span := tracer.Start(ctx, "command.process",
    trace.WithSpanKind(trace.SpanKindConsumer))

The fan-in exception. An aggregated reminder delivery bundles occurrences created by several unrelated actions, so it has no single parent. It starts a new trace with one span link per occurrence, which keeps the causal graph honest instead of arbitrarily picking one parent.

11.4.3 What a span may and may not carry

Allowed

  • marum.correlation_id — short-lived, quotable by the user
  • marum.loan_ref — first 8 hex of a keyed HMAC of the loan ID: stable enough to follow one loan, not reversible
  • Counts, durations, iteration numbers, bucket names
  • Enumerations: command kind, strategy, tier, error code

Never

  • Any money.Amount, in any form
  • Telegram user ID or chat ID
  • Internal user UUID
  • Lender name, loan name, or free text the user typed
  • SQL arguments or request bodies

An error span records the error class and the correlation ID. The message shown to the user carries the same correlation ID, which is how a support conversation reaches the right trace without anyone pasting a balance into a chat.

11.4.4 Sampling

At MVP scale, sample everything. Grafana Cloud meters logs and traces separately and on three axes — processed, written, and retained as GB-months — each with its own 50 GB free allowance per signal:

At 5,000 usersWritten / moRetained (14 d)FreeBinds at
Traces — 74,700 spans/day2.14 GB1.00 GB-mo50 GB~117,000 users
Logs — 26,440 lines/day0.33 GB0.15 GB-mo50 GB~758,000 users

100% head sampling uses about 4% of the trace allowance and removes an entire class of "the interesting request wasn't sampled" investigation. Revisit at 25 GB written per month, and then move to tail sampling that keeps every error, every span over 1 s, and 10% of the rest — never a blanket ratio.

// The handler drops, before anything is serialised:
//   - any attribute whose value is a money.Amount (type switch, not name match)
//   - any key in the denylist: amount, balance, principal, payment, chat,
//     telegram_id, token, secret, payload, body
//   - any value longer than 512 bytes
// A unit test asserts a log line built from a fully populated LoanState
// contains none of the digits of its balance.

11.5.3 Loki label policy

Loki bills and indexes by label. Only service_name, deployment_environment and level become labels — nine streams in total. trace_id, correlation, command and loan_ref go into structured metadata, which is queryable and filterable without creating a stream per value. Promoting trace_id to a label would create one stream per request and is the single fastest way to break a Loki tenant.

11.6.3 The version-label trap

Do not put service.version in resource attributes

Resource attributes become metric labels. Free-tier billing counts active series per month, so a label that changes on every deploy multiplies the whole catalogue by the number of releases:

Deploys / monthMonthly active seriesFree tier (10,000)
49,264fits, barely
1023,160over — $6.50 per extra 1k
3069,480far over

The version belongs on marum_build_info — one series per build — and on spans and profile tags, where it is an attribute rather than a series dimension. The same reasoning bans pod and container_id; service.instance.id is stable per deployment slot, not per restart.

11.7 Continuous profiling

Metrics say the p99 moved. Traces say which span. Profiles say which function, on which line. Without them every CPU or memory question ends in a guess, or in a local reproduction that does not reproduce.

func startProfiler(cfg Config) (*pyroscope.Profiler, error) {
    runtime.SetMutexProfileFraction(0)   // off by default — see the type table
    runtime.SetBlockProfileRate(0)

    return pyroscope.Start(pyroscope.Config{
        ApplicationName:   "marum",
        ServerAddress:     cfg.PyroscopeAddr,
        BasicAuthUser:     cfg.PyroscopeUser,
        BasicAuthPassword: cfg.PyroscopeToken,
        UploadRate:        60 * time.Second,   // see 11.7.2 — not the default
        Tags: map[string]string{
            "env":      cfg.Env,
            "instance": cfg.InstanceID,
            "version":  cfg.Version,   // safe here: profile tags are not metric series
        },
        ProfileTypes: []pyroscope.ProfileType{
            pyroscope.ProfileCPU,
            pyroscope.ProfileAllocObjects,
            pyroscope.ProfileAllocSpace,
            pyroscope.ProfileInuseObjects,
            pyroscope.ProfileInuseSpace,
        },
    })
}
Profile typeMVPReason
CPUOnReplay and the bisection solver are the only CPU-heavy paths; a regression shows here first.
Alloc objects / spaceOnAllocation churn in schedule building is the likeliest source of GC pressure.
In-use objects / spaceOnA leak in a long-lived process is invisible until it is an outage.
GoroutinesOffEnable while investigating a suspected leak; the runtime goroutine metric already alerts on the symptom.
Mutex, blockOffBoth add runtime overhead and double profile volume. Temporary settings when contention is suspected — the single-leader sender makes it unlikely.

11.7.1 Span profiles — the part that earns its keep

The profiler tags every sample with the span active at the time, so a slow span in Tempo links to the CPU profile of that span rather than a process-wide average. One line of wiring, already shown in §11.3:

otel.SetTracerProvider(otelpyroscope.NewTracerProvider(tp))

That turns "the plan computation was slow for this user last Tuesday" into a flame graph of exactly that computation, fourteen days later, with no reproduction.

11.7.2 Volume

Profiles are metered like logs and traces — 50 GB written per month on the free tier. Volume is upload interval × profile types × instances, and payload size is not knowable in advance:

IntervalTypesInstancesPushes / mo@10 KB@20 KB@30 KB

Roll out by measurement, not estimate: enable on one instance, read the real figure in Cost Management after 48 hours, extrapolate, then enable the second. The guardrail alert fires at 40 GB regardless.

11.8 Synthetic monitoring and load

Everything above observes real traffic. Two things observe its absence.

11.8.1 The synthetic check

One HTTP check, two probe locations, 60-second interval, against the authenticated status endpoint. It asserts more than a 200:

AssertionCatches
HTTP 200 within 2 sThe public path is down, or Cloudflare is not reaching the origin
tick_age_seconds < 300The scheduler has silently stopped — the failure most likely to go unnoticed
sender_leader == 1Nothing is sending, or two things are
oldest_pending_command_s < 120Commands are accepted but not applied
db_reachable == trueThe application is up but the database is not

The check runs from outside our infrastructure and depends on none of it. That is the point: it has to work when the thing it watches does not.

11.8.2 Load testing

k6 at phase gates rather than continuously — 500 virtual-user hours per month on the free tier, and four runs of 200 VUs for 15 minutes is about 200 of them. Scenarios are those in §9: the 09:00 quiet-hours release, a salary-day peak, 24-hour outage recovery, a mass 429 wave, and a deploy while commands and deliveries are leased.

Each probe location counts as an execution

11.12.4 The rules that keep it free

  1. No unbounded metric label, ever. Reviewed on every pull request; service.version stays out of resource attributes (§11.6.3).
  2. One synthetic check, at most two probes, 60-second interval. Changing any of the three means redoing the arithmetic.
  3. Profiles upload every 60 seconds, five types. Shorter intervals and the mutex, block and goroutine types are temporary investigation settings, reverted afterwards.
  4. Never open the Application Observability UI. Using it starts a host-hour meter that sending OTLP alone does not.
  5. Host-hour products stay off — Database Observability and Kubernetes Monitoring for the same reason.
  6. Two application instances. A third is affordable on every meter; a fourth needs the budget re-checked.
  7. Nothing important lives only in Grafana. Retention is 14 days — incident write-ups, drift investigations and golden fixtures are copied into the repository.
  8. Alert at 80% of every meter (§11.11), so the first sign is a ticket rather than an invoice.

11.12.5 What would actually force Pro

In the order they are likely to arrive: a fourth person needing a Grafana login ($8/month), metric retention beyond 14 days to compare this quarter's drift against last quarter's, or an uptime SLA becoming a commitment to paying customers. None is a volume problem and none arrives before Phase 4.

Pro is $19/month plus usage. If it becomes necessary the cost is small — but it should be a chosen upgrade, not an overage discovered in a bill, which is the purpose of 11.12.3 and the guardrail alerts.

12 · Release and migration

  1. Expand. Additive migration, compatible with the running binary.
  2. Verify. CI runs the previous release's integration suite against the expanded schema. This matters more than up → down → up.
  3. Deploy dual-schema code.
  4. Smoke in production: webhook echo, tick, replay, claim queries, database round trip.
  5. Backfill in a separate idempotent, resumable, observable job — never inside a migration.
  6. Switch reads and writes.
  7. Contract in a later release, once nothing reads the old representation.

Binary rollback never requires a schema rollback. Immutable financial data is never mechanically rewritten without a versioned migration report and a replay comparison. Production and the cloud test environment share a binary, a PostgreSQL major version and a migration path; the test environment exists with its own bot token and database before public beta.
